# Версионирование и релизы SkillCue

Единая схема, чтобы номера версий были предсказуемыми, а автообновление
десктопа работало без ручной возни.

## 1. Схема номеров — SemVer (`MAJOR.MINOR.PATCH`)

`vMAJOR.MINOR.PATCH`, например `v0.4.2`. Смысл частей для нашего продукта:

| Часть | Когда увеличиваем | Примеры |
|-------|-------------------|---------|
| **MAJOR** | Ломающее изменение для пользователя: несовместимый формат лицензий, смена протокола live, переезд на новый гейтвей | `1.0.0` → `2.0.0` |
| **MINOR** | Новая функция без ломки: новый STT-движок, режим интервью, экран | `0.4.0` → `0.5.0` |
| **PATCH** | Багфиксы, тексты, мелкая полировка | `0.4.1` → `0.4.2` |

**Сейчас мы в `0.x`** — это официальный «бета/до-релизного» диапазон SemVer: до
`1.0.0` можно двигаться быстро, MINOR может нести и мелкую ломку. `1.0.0`
выпускаем, когда продукт стабилен и пошли платящие пользователи.

Правило разрешения споров: если сомневаешься между MINOR и PATCH — бери MINOR;
между MAJOR и MINOR в `0.x` — бери MINOR.

## 2. Один источник правды

Версия живёт в **`apps/desktop/package.json` → `"version"`**. Отсюда её берёт
electron-builder для сборки, имени установщика и `latest.yml` автообновления.
Git-тег обязан совпадать: `package.json = 0.4.2` ⇔ тег `v0.4.2`.

Остальные release-метаданные синхронизируются и проверяются
`tools/verify_release_metadata.mjs`; одного изменения desktop/package.json
недостаточно. Полный список — в `RELEASE_BUILD_GUIDE.md`.

Dev и Alpha — отдельные установки с собственными данными. Alpha-конфигурация
берёт следующий patch и суффикс commit: из исходников `0.1.13` собирается
`0.1.14-alpha.g<commit>`. Номер Alpha не понижает и не заменяет Stable.
Автообновление публичного канала включено только для Windows Stable.

## 3. Conventional Commits (уже используем)

Сообщения коммитов: `type(scope): описание`. Типы определяют, какую часть версии
двигать при следующем релизе:

- `feat:` → MINOR
- `fix:` → PATCH
- `docs:` / `chore:` / `refactor:` / `test:` → без бампа сами по себе
- `feat!:` или футер `BREAKING CHANGE:` → MAJOR

Примеры из истории репозитория: `feat(stt): …`, `fix(ui): …`, `docs(design): …`.

## 4. Как выпустить релиз (пошагово)

1. Выбери проверяемый исходный commit без незакоммиченного кода; не смешивай
   экспериментальные изменения с исправлением для всех пользователей.
2. Синхронизируй метаданные версии, описание изменений и исходный тег. Не
   переиспользуй номер опубликованной версии для другого установщика.
3. Выполни проверки из `RELEASE_BUILD_GUIDE.md`, затем собери и проверь именно
   Stable installer с обычной пользовательской лицензией в отдельном профиле/VM.
4. CI и Release сейчас используют **ручной `workflow_dispatch`**. Пуш тега
   самостоятельно **не запускает** сборку или публикацию. Запускай workflow
   явно с выбранным ref либо используй проверенный локальный процесс из инструкции.
5. Публикуй проверенные байты установщика и blockmap, затем `latest.yml`.
   Проверь скачивание, хеш и обновление старой Stable с сохранением её данных.

Dev и Alpha публиковать в Stable Release нельзя: их отдельные установщики
доставляются вручную. Не включай автоматические платные runners ради совпадения
со старым описанием процесса.

## 5. Что должно совпадать (иначе автообновление сломается)

- `apps/desktop/package.json` version **==** git-тег (без `v` в package.json, с `v` в теге).
- **Раздельные репозитории (осознанно):** код — приватный `GalievGleb/interview`,
  релизы/установщики — публичный `GalievGleb/SkillCue`. Поэтому все три места
  должны указывать на `SkillCue`:
  - `apps/desktop/package.json → build.publish.repo = "SkillCue"` (сюда
    electron-builder публикует и отсюда electron-updater берёт обновления);
  - `download_url` лидбота (`tools/leadbot/config.json`) → `…/SkillCue/releases/latest`;
  - ссылки «Скачать» на лендинге → тот же `…/SkillCue/releases/latest`.
  - CI (`release.yml`) должен получать `GH_TOKEN` с правом публикации в `SkillCue`.

## 6. CHANGELOG.md

Держим человекочитаемый список в `CHANGELOG.md` в формате Keep a Changelog:
секции `Added / Changed / Fixed` под каждой версией. Заполняем при релизе из
коммитов между прошлым и новым тегом:

```bash
git log v0.4.2..HEAD --pretty="- %s"
```

## 7. Быстрая шпаргалка

```
Багфикс          → PATCH (0.4.1 → 0.4.2), коммиты fix:
Новая фича        → MINOR (0.4.2 → 0.5.0), коммиты feat:
Ломка/1.0         → MAJOR, feat!: или BREAKING CHANGE
Stable-релиз      → метаданные → проверки → Stable installer → приёмка → явная публикация
Dev/Alpha         → отдельная сборка → тесты → отдельный установщик, без Stable feed
```
