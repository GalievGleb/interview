# Быстрый текстовый ответ в оверлее SkillCue

Дата: 2026-08-01

## Проблема

Если в live-оверлее нет финального транскрипта разговора, действие «Подсказка»
автоматически переходит на анализ экрана. Условие не учитывает, что пользователь
мог уже ввести полноценный текстовый вопрос. В результате запрос вроде «что такое
тестирование» делает скриншот, загружает изображение и вызывает vision-модель.
Это увеличивает время до первого текста и расход токенов без пользы для ответа.

## Согласованное поведение

- Любой непустой текст пользователя считается достаточным контекстом и всегда
  отправляется как текстовый запрос. Автоматический скриншот для него запрещён.
- Явное действие «Экран» всегда сохраняет текущий vision-сценарий.
- Автоматический анализ экрана остаётся только для «Подсказки», когда одновременно
  отсутствуют и введённый текст, и транскрипт разговора, а настройка анализа экрана
  включена.
- Обычный текстовый запрос использует быстрый режим. Включённый пользователем
  Smart сохраняет глубокий, более медленный режим.
- Нажатие `Ctrl+Enter` немедленно открывает карточку ответа. Вместо отдельной
  строки «Реплика отправлена — готовлю ответ» внутри карточки показывается
  пульсирующая точка до первого токена, затем ответ стримится туда же.

## Маршрутизация

Решение о маршруте выделяется в маленькую чистую функцию со следующими входами:
действие, наличие пользовательского текста, наличие транскрипта, доступность и
разрешение захвата экрана, состояние Smart. Результат — один из маршрутов:

- `text-fast`: непустой текст при выключенном Smart;
- `text-deep`: непустой текст при включённом Smart;
- `text-general`: действие на основе транскрипта без пользовательского текста;
- `screen`: явное действие «Экран» либо пустая «Подсказка» без транскрипта;
- `notice`: нет ни одного доступного источника контекста.

Компонент оверлея только исполняет выбранный маршрут. Это исключает повторение
условий и позволяет проверить поведение без запуска Electron.

## Сценарий Ctrl+Enter

Сейчас горячая клавиша сначала просит STT принудительно финализировать текущий
аудиобуфер. Уже распознанная финальная реплика из транскрипта рассматривается
только если отправить команду финализации не удалось. Поэтому пустой аудиобуфер
может оставить интерфейс в уведомлении без LLM-запроса, хотя вопрос уже виден.

Новый порядок:

1. Если есть ещё не обработанная финальная реплика триггерного аудиоканала
   (собеседника, а при одном микрофоне — последняя распознанная реплика), сразу
   запустить ответ по ней — без дополнительного STT-запроса.
2. Если финальной реплики ещё нет, но речь продолжается, отправить `finalize` в STT.
3. Сразу после горячей клавиши создать карточку `Подсказка`. В правом bubble
   показать вопрос, если он известен, иначе временную подпись `Ctrl+Enter · Подсказка`.
   Пока STT финализируется или модель ещё не прислала первый токен, в теле карточки
   видна пульсирующая точка.
4. После получения финального текста заменить временную подпись фактическим
   вопросом и стримить ответ в ту же карточку без скачка интерфейса.
5. Если вопрос получить не удалось либо запрос завершился ошибкой, показать ошибку
   в этой карточке. Не оставлять бесконечную загрузку и не переносить состояние в
   отдельную жёлтую строку.

Для UI используются явные фазы `finalizing-transcript`, `waiting-first-token`,
`streaming`, `done` и `error`. Карточка существует во всех фазах после нажатия.

## Быстрый backend-путь

Для режима `fast` endpoint `/chat` не выполняет сетевой поиск embeddings/RAG.
Переданный транскрипт остаётся доступен как явный контекст. Модель выбирается
продуктовым роутером для fast-режима; запрос провайдеру получает приоритет
пропускной способности, минимальный reasoning и уменьшенный лимит ответа,
достаточный для короткой подсказки на собеседовании.

General и deep сохраняют существующий RAG и текущие лимиты, поэтому подробные
ответы и Smart не теряют контекст документов.

## Ошибки и отмена

Отмена предыдущего запроса перед новым остаётся без изменений. Ошибка fast-запроса
показывается в текущей карточке и не запускает vision автоматически: скрытый
fallback снова сделал бы простой запрос медленным и непредсказуемым. Пользователь
может явно нажать «Экран», если текстового контекста недостаточно.

## Проверка и критерии готовности

- Unit-тест маршрутизации: непустой текст никогда не выбирает `screen`.
- Unit-тесты остальных маршрутов, включая Smart и пустую «Подсказку».
- Unit-тест `Ctrl+Enter`: уже финальный вопрос запускается сразу и не вызывает
  дополнительный STT `flush`.
- Unit-тест `Ctrl+Enter`: незавершённая речь показывает карточку ожидания, затем
  переходит в стриминг либо явную ошибку без зависания.
- Backend-тест: `fast` пропускает RAG, передаёт fast-опции стриму и сохраняет
  явный контекст.
- Регрессионные desktop/backend-тесты, линтер, typecheck и production-сборка.
- В собранном приложении текстовый вопрос не помечается «Смотрел экран».
- После `Ctrl+Enter` карточка с индикатором появляется в следующий render-frame;
  строка «Реплика отправлена — готовлю ответ» не отображается.
- Целевое время до первого фрагмента текста при нормальной сети — 1–2 секунды;
  внешняя задержка провайдера может выходить за этот диапазон, но в клиенте не
  должно быть блокирующих screen/RAG-этапов.

## Доставка

Изменение выпускается следующей версией через уже работающий встроенный updater;
ручное скачивание приложения не требуется.
